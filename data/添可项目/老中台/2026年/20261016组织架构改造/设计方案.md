# 大区（SALE_AREA）缓存化 + 大区→分部层级关系改造方案
（分部 DISTRIBUTOR_SALE_AREA 保持不变）

## 一、目标与现状

**现状**
- `SALE_AREA`：字典 `Map<大区编码, 大区名称>`（平台字典，外部 jar）—— **本次要改造的对象**。
- `DISTRIBUTOR_SALE_AREA`：字典 `Map<分部编码, 分部名称>`（平台字典，所有分部扁平表）—— **本次不改造，原样保留**。
- 大区→分部的层级关系：目前隐含在平台字典里——每个"大区编码"本身又是一个 `BizDictionaryType`，其字典值 = `Map<分部编码, 分部名称>`。本期把这份"隐藏"的层级关系显式接管到自己的配置缓存里。

**目标**
1. 把"大区列表"从平台字典 `SALE_AREA` 迁到自己的配置缓存（`ConfigKeyConstant` 体系），不再依赖外部 `BizDictionary.SALE_AREA`。
2. 把"大区→分部"的层级归属关系用一份配置管理起来（**基于 `DISTRIBUTOR_SALE_AREA` 里已有的分部编码**，不重复维护分部名称）。
3. **不动 `DISTRIBUTOR_SALE_AREA` 的任何调用点**——分部依旧是分部，名称仍由平台字典提供。

**与旧方案的关键区别**
- 旧方案：把 `SALE_AREA` 和 `DISTRIBUTOR_SALE_AREA` 全部迁到一份 JSON（含分部名称），约 200+ 处 `DISTRIBUTOR_SALE_AREA` 调用点要批量改写。
- 新方案：只迁 `SALE_AREA`（大区）和"大区→分部编码"的层级关系；`DISTRIBUTOR_SALE_AREA` 完全不动。配置里只存"大区→分部编码列表"，分部名称在运行时从 `DISTRIBUTOR_SALE_AREA` 取，避免重复维护、避免改动 200+ 处。

## 二、缓存配置设计

### 1. 新增配置 Key（`ConfigKeyConstant.java`）
```java
// 大区及大区下分部配置（JSON），替代 BizDictionary SALE_AREA 及"大区→分部"层级关系
// 注意：只管"层级归属"，分部名称仍来自 DISTRIBUTOR_SALE_AREA
public static final String SALE_AREA_CONFIG = "sale_area_config";
```

### 2. JSON 结构（写入 `sys_config` 表，key=`sale_area_config`）
```json
{
  "SA_HN": { "name": "华南大区", "regions": ["GZ", "SZ"] },
  "SA_HD": { "name": "华东大区", "regions": ["SH", "HZ"] },
  "OTHER_REGION": { "name": "其他", "regions": [] }
}
```
说明：
- `name`：大区名称（原 `SALE_AREA` 的值）。
- `regions`：**分部编码列表**（仅编码，不含名称）。这些编码必须存在于 `DISTRIBUTOR_SALE_AREA` 中。
- 分部名称一律以 `DISTRIBUTOR_SALE_AREA` 为准，本配置不冗余存名称。

从这份结构可派生：
- 大区 map：`SA_HN→华南大区`（原 `SALE_AREA`）
- 大区下分部编码：`SA_HN→[GZ,SZ]`（原 `valueOf(大区编码)` 的 keySet）
- 大区下分部编码→名称：`SA_HN→{GZ:广州分部, SZ:深圳分部}`（编码来自本配置，名称来自 `DISTRIBUTOR_SALE_AREA`）
- 分部→大区反查：`GZ→SA_HN`（原 `BaseOrganizationAreaConfigServiceImpl` 的遍历反查）

## 三、封装缓存读取（核心改动）

新建 `SaleAreaCacheManager`（参考 `BizDictionaryCacheManager` 的懒加载/缓存思路），内部从 `ConfigCacheManager.getConfigValue(SALE_AREA_CONFIG)` 解析 JSON 并构建派生 map，提供统一 API：

```java
public class SaleAreaCacheManager {
    // 大区编码 -> 大区名称（含 OTHER_REGION）
    public static Map<String,String> getSaleAreaMap();
    // 大区名称便捷取值
    public static String getSaleAreaName(String code);
    // 大区编码 -> 该大区下的 分部编码->名称（编码来自本配置，名称取自 DISTRIBUTOR_SALE_AREA）
    public static Map<String,String> getRegionsByArea(String areaCode);
    // 分部编码 -> 所属大区编码（基于层级关系反查）
    public static String getAreaByRegion(String regionCode);
}
```
说明：
- `getSaleAreaMap()` 返回形态与 `getBusinessDictionary(SALE_AREA)` 一致（`Map<String,String>`），A 组调用点可机械替换。
- `getRegionsByArea()` 返回形态与原 `valueOf(area)` 一致（`Map<分部编码, 分部名称>`），C 组调用点可机械替换；名称解析若取不到则回退用编码。
- `getAreaByRegion()` 取代原来"遍历 SALE_AREA + valueOf"的反查逻辑，O(1) 完成。

## 五、实施步骤（建议按阶段）

1. **准备配置**：在 `ConfigKeyConstant` 增加 `SALE_AREA_CONFIG`；在配置后台 / `sys_config` 写入 JSON（含 `OTHER_REGION`，`regions` 仅填分部编码）。
2. **封装读取**：新建 `SaleAreaCacheManager`，实现第③节 API，内部 JSON 解析 + 本地缓存（带 TTL 或监听配置变更刷新）；`getRegionsByArea` 在解析时按编码从 `DISTRIBUTOR_SALE_AREA` 补名称。
3. **灰度替换 A 组**（大区，约 22 处）：改动小、影响面清晰，先验证页面下拉、统计报表名称正确。
4. **替换 B 组**（大区→分部）：逻辑等价替换，重点验证培训统计按大区下分部过滤、门店 workspace 大区下分部下拉。
5. **替换 C 组**（分部→大区 反查）：删掉遍历逻辑，验证组织区域反查正确。
6. **清理**：确认无 `BizDictionaryType.SALE_AREA` 引用（反查里的 `valueOf` 一并清除）后，平台字典 `SALE_AREA` 可下线；`DISTRIBUTOR_SALE_AREA` 保持不动。`SALE_AREA` 作为 `BizDictionaryType` 枚举若仍被平台其他字典使用则保留，仅本服务不再引用。

## 六、风险与注意点

- **分部名称单一来源**：本期所有"分部名称"仍以 `DISTRIBUTOR_SALE_AREA` 为准，配置里不冗余存名称；`getRegionsByArea` 取不到名称时回退用编码，避免空指针。
- **层级配置与分部表一致性**：JSON 里 `regions` 的分部编码必须能在 `DISTRIBUTOR_SALE_AREA` 中找到；新增/调整分部时，两处都要同步（建议把"新增分部"流程同时维护层级配置，或脚本校验）。
- **`OTHER_REGION` 过滤**：现有多处有 `remove("OTHER_REGION")`，新 map 里保留该 key 并维持同样 remove 逻辑，行为保持一致。
- **缓存刷新**：配置变更后需能热更新（参考 `ConfigCacheManager` 是否支持变更失效）；否则改完配置要重启。
- **影响面收窄**：相比旧方案（改 ~200 处分部 + 22 处大区），本期只动 ~33 处大区相关调用点，风险大幅下降。
