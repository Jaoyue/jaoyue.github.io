# 测试管理功能设计文档

## 1. 文档概述

### 1.1 目的

本文档用于指导「项目管理 → 测试管理」模块的功能开发。测试管理承接蓝图方案（需求清单、系统功能清单）与开发任务管理（开发架构设计、开发方案设计、开发任务清单）的输出，形成一套覆盖 **测试计划 → 测试方案 → 测试用例 → 测试报告** 的完整质量保障闭环。

### 1.2 适用范围

- 项目维度：与开发任务管理共用同一 `projectId / projectCode`，所有数据按项目隔离。

- 功能范围：测试计划、测试方案、测试用例、测试报告四个 Tab。

- 用户角色：项目经理、测试负责人、开发人员、守门人。

### 1.3 设计原则

1. **与开发任务管理对齐**：复用其成熟的 AI 异步编排、守门确认、版本快照、编号分配、异步轮询机制。

2. **渐进式改造**：已有「测试用例」「测试报告」保持核心数据结构与业务能力不变；新增「测试计划」「测试方案」按新架构实现，并建议后续将测试用例/报告逐步迁移至统一策略架构。

3. **上下游强依赖**：AI 生成测试计划前必须已完成需求清单和系统功能清单的守门确认；生成测试方案前必须已有测试计划；生成测试用例前必须已有测试方案。

4. **数据可追溯**：每次 AI 生成均记录 `rev_ai_request_log`，保留 AI 原文与人工终稿，用于采纳率分析。

## 2. 页面结构与 Tab 导航

根据 UI 截图，测试管理模块页面结构如下：

### 2.1 测试计划 Tab

- **页面标题**：测试计划

- **数据来源**：需求清单 + 系统功能清单

- **空态**：未生成时显示红色「未完成」标签，提示「测试计划尚未完成，请通过 AI 助手生成」，并提供「AI 助手」按钮。

- **生成后展示**：Markdown / 富文本形式的测试计划内容，支持编辑、保存、重新生成。

### 2.2 测试方案 Tab

- **页面标题**：测试方案

- **数据来源**：测试计划

- **空态**：未生成时显示红色「未完成」标签，提示「测试方案尚未完成，请通过 AI 助手生成」，并提供「AI 助手」按钮。

- **生成后展示**：按测试维度（功能测试、性能测试、安全测试、兼容性测试等）组织的测试方案，支持编辑、保存、重新生成。

### 2.3 测试用例 Tab

- **页面标题**：测试用例

- **数据来源**：需求清单 + 系统功能清单 + 测试方案

- **筛选区**：编码、标题、模块、关联功能、任务名称、优先级、重要程度、测试场景、执行结果、执行人、创建人、创建时间、执行时间等。

- **操作区**：「新建用例」「创建 Bug」「AI 助手」。

- **表格列**：序号、编码、标题、模块、关联功能、任务名称、优先级、重要程度、测试场景、执行结果、执行人、创建人、创建时间、适用阶段、操作（编辑/创建 Bug/删除/执行）。

- **行操作**：执行用例、编辑、创建 Bug、删除。

### 2.4 测试报告 Tab

- **页面标题**：测试报告

- **数据来源**：测试用例执行结果 + Bug 数据

- **空态**：提示「尚未生成测试报告，点击生成测试报告按钮，AI 将根据测试用例执行结果和 Bug 信息生成测试报告」。

- **操作**：「生成测试报告」按钮。

- **生成后展示**：报告内容（Markdown）、关联 Bug 列表、评论、反馈（有帮助/无帮助）。

## 4. 公共机制

### 4.1 AI 异步编排（新架构）

新增「测试计划」「测试方案」采用与开发任务管理一致的 `AiChatOrchestrator + AiBusinessTypeStrategy` 模式：

**新增策略类**：

- `PmTestPlanStrategy`：业务类型编码建议 `PM_TEST_PLAN`，businessType 建议 `1301`。

- `PmTestSolutionStrategy`：业务类型编码建议 `PM_TEST_SOLUTION`，businessType 建议 `1302`。

**建议将测试用例、测试报告逐步迁移**：

- 新增 `PmTestCaseStrategy`（businessType 沿用 `1000`）和 `PmTestSolutionStrategy`（businessType 沿用 `1100`），替换旧的 `AsyncAiChatService.submitAsyncTask` 调用，统一走 `AiChatOrchestrator`。

- 迁移后需在 `BusinessTypeEnum` 中保留原枚举值即可，策略类通过 `getBusinessType()` 返回对应 code。

### 4.2 守门确认机制

测试计划、测试方案、测试用例（AI 生成批次）均采用「AI 产出先入库为待守门状态，人工确认后转为正式内容」的机制：

|   |   |   |   |
|---|---|---|---|
|子模块|守门前状态|守门动作|守门后状态|
|测试计划|`WAITING_GATEKEEPER`|编辑/确认保存|`CONFIRMED`|
|测试方案|`WAITING_GATEKEEPER`|编辑/确认保存|`CONFIRMED`|
|测试用例|AI 生成后暂存或标记为未生效|批量保存/编辑|正式生效|
|测试报告|AI 生成后暂存|编辑/确认保存|正式生效|

**守门约束**：

- 已确认（`CONFIRMED`）的测试计划和测试方案不允许再次 AI 生成，除非先重置为草稿/待守门状态。

- 已确认的内容允许人工编辑，但编辑后需记录操作日志。

### 4.3 编号分配规则

沿用开发任务管理的编号规则：前缀 + 日期（yyMMdd）+ 6 位流水，按天全库递增，`synchronized` 分配。

|   |   |   |
|---|---|---|
|子模块|前缀|示例|
|测试计划|ATTP|ATTP260914000001|
|测试方案|ATTS|ATTS260914000001|
|测试用例|ATTC|ATTC260914000001|
|测试报告|ATTR|ATTR260914000001|

### 4.4 异步轮询

前端统一使用 `POST /pm/ai/generateStatus` 查询所有 AI 生成任务状态，或在提交后使用 `AiChatOrchestrator.getTaskStatus(requestId)` 轮询。

## 5. 测试计划子模块设计

### 5.1 业务目标

根据蓝图方案中的需求清单和系统功能清单，调用 AI 工作流生成项目级测试计划，明确测试范围、测试策略、测试阶段、资源安排、准入准出标准等。

**表名**：`pm_test_plan`（建议与开发任务管理同 schema，便于统一项目视图）

|   |   |   |
|---|---|---|
|字段名|类型|说明|
|id|BIGINT / STRING|主键|
|code|VARCHAR(32)|测试计划编码，ATTP 前缀|
|project_id|VARCHAR(64)|项目ID|
|project_name|VARCHAR(128)|项目名称|
|project_code|VARCHAR(64)|项目编码|
|product_id|BIGINT|产品ID|
|name|VARCHAR(256)|计划名称|
|content|LONGTEXT|计划内容（Markdown）|
|ai_content|LONGTEXT|AI 原文|
|final_content|LONGTEXT|人工终稿|
|status|VARCHAR(32)|WAITING_GATEKEEPER / CONFIRMED|
|gatekeeper_id|VARCHAR(64)|守门人账号|

|confirmed_at|DATETIME|确认时间|
|creator_id|VARCHAR(64)|创建人|
|creator_name|VARCHAR(64)|创建人姓名|
|create_time|DATETIME|创建时间|
|update_time|DATETIME|更新时间|
|is_deleted|TINYINT|删除标记|

### 5.3 接口设计

|   |   |   |
|---|---|---|
|接口|方法|说明|
|POST /pm/test-plan/detail/{projectId}|GET / POST|获取当前项目测试计划详情|
|POST /pm/test-plan/generate|POST|根据需求清单+系统功能清单生成测试计划（提交 AI 任务）|
|POST /pm/test-plan/saveOrUpdate|POST|保存/编辑测试计划（含守门确认）|
|POST /pm/test-plan/regenerate|POST|重新生成（仅 WAITING_GATEKEEPER 或 CONFIRMED 状态下允许重置后生成）|

### 5.4 AI 生成流程

1. **校验**：查询 `pm_blueprint_requirement` 和 `pm_blueprint_system_feature`，确认当前项目存在 `CONFIRMED` 状态记录。

2. **组装 formData**：
    
    - `projectId` / `projectName` / `projectCode`
    
    - `requirements`：需求清单数组（名称、描述、优先级）
    
    - `systemFeatures`：系统功能清单数组（名称、描述、关联需求）

3. **提交 AI**：`aiChatOrchestrator.submitAsyncTask("PM_TEST_PLAN", projectCode, requestId, formData)`

4. **回调处理**：`PmTestPlanStrategy.processAiResult` 解析 Markdown 内容，写入 `pm_test_plan`，状态设为 `WAITING_GATEKEEPER`。

5. **前端轮询**：展示生成结果，支持编辑后确认。

## 7. 测试用例子模块设计

### 7.1 业务目标

基于需求清单、系统功能清单和测试方案，生成并管理可执行的测试用例，支持手工创建、AI 生成、Excel 导入导出、执行记录、创建 Bug。

### 7.2 现有能力梳理

已有代码覆盖：

- `PmTestCaseController`：分页、详情、新增/编辑、删除、执行、生成、批量保存、导出、导入、导出模板。

- `RevTestCase`：测试用例主表（`rev_test_case`）。

- `RevTestCaseStep`：测试步骤表（`rev_test_case_step`）。

- `RevTestCaseExecution` / `RevTestCaseExecutionStep`：执行记录与执行步骤。

- 编号前缀 `ATTC`，result 字段（未执行/通过/失败/忽略）。

### 7.3 建议改造点

1. **AI 生成入口改造**：
    
    - 当前 `generate` 接口按任务维度（`projectTaskId`）生成。
    
    - 新需求下，测试用例生成应基于项目维度：需求清单 + 系统功能清单 + 测试方案。
    
    - 建议新增 `PmTestCaseStrategy` 接入 `AiChatOrchestrator`，businessType 沿用 `1000`。
    
    - `generate` 接口入参改为项目级：`projectId`、`projectName`、`productId`，不再强制要求任务维度字段。
    
    - AI 返回结构化 JSON 数组，字段包括：`title`、`systemName`、`userRequirement`、`systemFeature`、`moduleName`、`priority`、`preconditions`、`applyPhase`、`scenario`、`steps`。

2. **增强关联字段**：
    - `system_feature_id` 字段已存在，建议新增 `requirement_code`、`feature_code` 用于关联蓝图需求/功能。

3. **分组展示**：
    - 列表按「模块 + 关联功能」分组，未匹配到模块的用例归入「未归属模块」。

4. **创建 Bug**：
    - 行操作「创建 Bug」调用现有 `IPmBugService` 创建项目 Bug，并记录用例与 Bug 的关联关系（可选新增中间表 `pm_test_case_bug` 或扩展字段）。

### 7.4 接口设计（在现有基础上调整）

|   |   |   |
|---|---|---|
|接口|方法|说明|
|POST /pm/test-case/pageList|POST|分页列表|
|GET /pm/test-case/detail/{id}|GET|详情|
|POST /pm/test-case/addOrUpdate|POST|新增/编辑|
|DELETE /pm/test-case/{id}|DELETE|删除（仅创建人）|
|POST /pm/test-case/execute|POST|执行用例|
|POST /pm/test-case/generate|POST|AI 生成（项目级）|
|POST /pm/test-case/batch-save|POST|守门确认：批量保存 AI 生成用例|
|POST /pm/test-case/export|POST|导出|
|POST /pm/test-case/importExcel|POST|Excel 导入|
|POST /pm/test-case/exportTemplate|POST|导出导入模板|
|POST /pm/test-case/createBug|POST|基于用例创建 Bug（新增建议）|

### 7.5 AI 生成流程

1. **校验**：需求清单、系统功能清单、测试方案均已 `CONFIRMED`。

2. **组装 formData**：
    
    - `projectId` / `projectName`
    
    - `requirements`：已确认需求清单
    
    - `systemFeatures`：已确认系统功能清单
    
    - `testSolution`：已确认测试方案内容

3. **提交 AI**：通过 `PmTestCaseStrategy` 或旧 `AsyncAiChatService` 提交。

4. **回调处理**：解析 JSON 数组，批量生成 `RevTestCase` + `RevTestCaseStep`，初始 result 为「未执行」。

### 7.6 状态说明

测试用例无复杂状态机，核心字段：

- `result`：未执行 / 通过 / 失败 / 忽略

- 每次执行产生一条 `RevTestCaseExecution` 记录，并更新 `RevTestCase.result` 为最新结果。

## 8. 测试报告子模块设计

### 8.1 业务目标

根据测试用例执行结果和 Bug 信息，调用 AI 工作流生成测试报告，支持人工编辑、关联 Bug、评论与反馈。

### 8.2 现有能力梳理

已有代码覆盖：

- `PmTestReportController`：分页、详情、保存/更新、删除、反馈、评论、生成、批量保存。

- `RevTestReport`：测试报告主表（`rev_test_report`）。

- `RevTestReportBug`：报告关联 Bug。

- `RevTestReportComment`、`RevTestReportFeedback`：评论与反馈。

- 编号前缀 `ATTR`。

### 8.3 建议改造点

1. **AI 生成入参增强**：
    
    - 当前 `generate` 仅传入 `projectId`、`projectName`、`productId`，Bug 列表由服务层查询。
    
    - 建议同时传入测试用例执行汇总数据（总数、通过数、失败数、忽略数、未执行数），使 AI 生成的报告更精准。

2. **迁移至新策略架构**：新增 `PmTestReportStrategy`（已存在，但使用旧回调方式），建议统一由 `AiChatOrchestrator` 调度。

### 8.4 接口设计（保持现有）

|   |   |   |
|---|---|---|
|接口|方法|说明|
|POST /pm/test-report/pageList|POST|分页列表|
|GET /pm/test-report/getDetail|GET|详情|
|POST /pm/test-report/saveOrUpdate|POST|保存/更新|
|POST /pm/test-report/delete|POST|删除|
|POST /pm/test-report/feedback|POST|提交反馈|
|POST /pm/test-report/cancelFeedback|POST|取消反馈|
|GET /pm/test-report/getUserFeedbackType|GET|当前用户反馈类型|
|POST /pm/test-report/comment|POST|提交评论|
|POST /pm/test-report/deleteComment|POST|删除评论|
|POST /pm/test-report/generate|POST|AI 生成测试报告|
|POST /pm/test-report/batch-save|POST|批量保存 AI 生成报告|

### 8.5 AI 生成流程

1. **查询数据**：
    
    - 当前项目下所有测试用例及执行结果。
    
    - 当前项目下所有 Bug 列表。

2. **组装 formData**：
    
    - `projectId` / `projectName`
    
    - `testCaseSummary`：{total, passed, failed, ignored, unexecuted}
    
    - `bugList`：Bug 详情数组

3. **提交 AI**：`aiChatOrchestrator.submitAsyncTask("PM_TEST_REPORT", projectId, requestId, formData)`

4. **回调处理**：`PmTestReportStrategy.processAiResult` 调用 `IPmTestReportService.processContent`，创建 `RevTestReport` 并关联 Bug。

## 11. 关键设计决策

### 11.1 新功能使用新架构，旧功能渐进迁移

- 测试计划、测试方案直接采用 `AiChatOrchestrator + AiBusinessTypeStrategy` 新架构。

- 测试用例、测试报告建议新增对应 Strategy 类，逐步替换旧的 `AsyncAiChatService` 调用，避免两套异步机制并存。

- 若时间紧张，可保留测试用例/报告旧方式，但需在文档和代码注释中明确标注待迁移。

### 11.2 新增表使用 pm_ 前缀

测试计划、测试方案与开发任务管理属于同一项目域，使用 `pm_` 前缀（`pm_test_plan`、`pm_test_solution`）更合理；测试用例、测试报告因历史原因在 `rev_` 前缀下，本次不做迁移。

### 11.3 业务类型编码规划

建议在 `BusinessTypeEnum` 中新增：

并在 `rev_basic_config` 中新增对应 `config_key`：`PM_TEST_PLAN_CREATE`、`PM_TEST_SOLUTION_CREATE`。

### 11.4 生成与持久化职责分离

为避免 `AiChatOrchestrator` 构造器循环依赖（该问题在开发任务管理中已有明确注释），Strategy 类中优先注入 Mapper 或延迟获取 Service Bean，而非直接注入业务 Service。

### 11.5 上游数据依赖校验

测试计划/方案/用例生成前均需校验上游数据状态，避免 AI 基于不完整数据生成低质量结果。建议将校验逻辑封装为 `PmTestDependencyService` 公共方法供各模块复用。
